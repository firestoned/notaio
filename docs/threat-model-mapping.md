# Mapping to the AgentSandbox threat model

Last full pass 2026-11-25, against ADR-0001 to ADR-0023 (ADR-0003 and ADR-0020 as amended 2026-11-21; ADR-0002, ADR-0006 and ADR-0008 as amended 2026-11-22; ADR-0022 is proposed, with nothing implemented to map; ADR-0023 without decision 7's bundle v4 fields, which are not built).

What this project implements, what it only supports, and what it does not cover. Identifiers refer
to the AgentSandbox Threat Model and Security Roadmap. When that document changes, update
`crates/sandboxpolicy-core/src/registry.rs` and `builtin.rs` in the same pull request.

## Implemented here

| Model item | How |
| --- | --- |
| Knob register (section 9), rule "one step at a time" | `registry.rs`, lint L011 |
| Expiring relaxations, per-step lifetime caps | lint L012, bundle `notAfter` clamped to the earliest grant expiry |
| Approver per knob | `registry.rs` approvers, lint L013 |
| "No toxic combinations" | lint L003, with `dataScope` for Lab; L020 makes Lab's "no sensitive data" true of its audiences (ADR-0017) |
| "Toxic-combination lint on every policy pull request" | `notaio lint` (`crates/notaio/src/lint.rs`, ADR-0006) runs the controller's own checks on the policy repository's files, with the same codes, and SARIF for inline review. A symlink inside the tree it walks is an input error, so a pull request can neither loop it nor have it read outside the tree, and no file goes unchecked. Making it a required check is a setting of the policy repository. |
| Lab-only knobs (K6.3 R1, K8.2 R1) | lint L004 |
| "Wildcard audiences are never allowed" (K5.3) | lint L005 |
| Read-only token scope by default (K5.2), token TTL ceilings (K5.1) | lint L006 |
| Lab audiences only (K5.2, K5.3 for Lab) | each ExposureCeiling audience carries a `dataScope`, set by Security, unset meaning `Internal`; a policy on a `LabOnly` profile exposing an audience not classified `LabOnly` publishes nothing (lint L020 in `lint_exposure`, in `notaio lint` and the controller; ADR-0017). Two ceilings that classify one audience differently are a warning in `notaio lint` (L021) |
| Egress default deny, no direct-IP egress (K4.1, T4.1) | lint L007 on direct egress; every audience endpoint is an exact name, never a wildcard or IP literal (L017), reached through the broker's proxy, so K4.1 R0 still means all calls are brokered; an endpoint is reachable one way only (L018). ADR-0013. With audience definitions on (ADR-0020), a definition's endpoints are exact names too (L017), one audience per endpoint within what a namespace sees (L025), and a grant's endpoints are a subset of its definition's, an empty list reaching nothing (L028). |
| Tool and MCP pinning (K1.3, T1.2) | lint L008 |
| Lease and egress volume ceilings (K7.3, K4.3) | lint L009, `ceilings.rs` |
| O3 "maximum exposure is computable from its policy" | `status.maxExposure`; for a composite (ADR-0023), of its effective content, its includes' audiences, egress and tools added, so a sandbox's exposure is still read from the one policy it names |
| Validation "maximum exposure compared with its approved ceiling" on every policy pull request | `ExposureCeiling` per policy, approved by `Security` (ADR-0007); `lint_exposure` (L014 to L016) runs in `notaio lint` and in the controller, grants included. No ceiling, or exposure it does not cover: no bundle (`e2e_bundle`). With audience definitions on, the granted audiences' definitions are compared too: their endpoints and `maxTtlSeconds` must be approved, so an audience a team writes opens nothing Security did not approve (`lint_definitions_against_ceiling`, L014, ADR-0020). A composite (ADR-0023) is compared on its effective content against its own ceiling, so Security approves the combination as one; an include's ceiling, grants and conditions bound nothing in it, and an include widened past a composite's ceiling stops that composite's re-signing (`evaluate`, `e2e_compose`). |
| T5.4 bundle downgrade or tampering | signed DSSE envelope, monotonic version, verification refuses a downgrade, a forged signature and a digest mismatch (`crates/sandboxpolicy-bundle/src/verify.rs`). The digest covers the RFC 8785 form of the content (`jcs.rs`, ADR-0005), so a consumer in any language can recompute it; content with no exact canonical form is refused, not approximated. The version floor a consumer keeps is persisted before a bundle is acted on, so a restart does not reopen the downgrade, and it is keyed by namespace and name with the incarnation's `uid` ordered by `issuedAt`, so a recreated policy is accepted and a replay from its old incarnation is refused (`floor.rs`, ADR-0008). `accept` takes the policy the consumer asked for and refuses another policy's valid bundle before the floor is read (`WrongSubject`, ADR-0008 decision 7). The file floor writes through an exclusively created, owner-only temporary file, never through a planted symlink. A consumer refuses a bundle signed to last more than one day, the controller's own maximum, so a misconfigured or compromised signer cannot issue one that outlives it (`LifetimeTooLong`, ADR-0002 decision 5 as amended). Both refusals are conformance vectors. A bundle no longer refreshed (its policy turned invalid) expires within one lifetime: 15 minutes by default, 5 minutes to a day, a value outside refused at startup (`cli.rs`, ADR-0018). `e2e_bundle` checks a wrong key and a downgrade across a consumer restart against the deployed controller. Audience bundles (ADR-0020) get the same checks under their own DSSE payload type and schema, so neither kind verifies as the other (`crates/sandboxpolicy-bundle/src/audience.rs`), and their own floor per audience namespace and name, apart from any policy's even in one store (`floor::accept_audience`); `e2e_audience` verifies a published one against OpenBao's key and refuses it as a policy bundle. |
| T8.2 signing key not held by administrators | The default deployment (`deploy/controller/`) signs with a non-exportable ed25519 OpenBao transit key (ADR-0004, `crates/notaio/src/openbao.rs`): notaio logs in with its ServiceAccount (projected token, audience `openbao`, TLS 1.3 against OpenBao's own CA) and may only request signatures; every request is in OpenBao's audit log. The controller refuses to start with both signers configured; the development seed is an opt-in patch for local experiments, used by no e2e suite. Accepted risk: a cluster administrator acting as notaio's ServiceAccount can request signatures, but cannot take the key. `e2e_openbao`. Audience bundles are signed by the same key with the same custody (`BundleSigner::sign_audience`). |
| Hard floor "policy bundles are signed, unsigned ones are rejected" | producer never publishes unsigned (`crates/notaio/src/reconcile.rs`: no signer, no bundle), consumer verification fails closed. Content without a canonical form is never compiled into a bundle (`evaluate`, `Ready=False, NotCanonical`). When the signer fails (OpenBao sealed or unreachable), nothing new is published and the policy reports `Ready=False, SigningFailed`, keeping the previous bundle's version and digest (`e2e_openbao`). The audience reconciler follows the same rules: no signer, no audience bundle (`Ready=False, NoSigner`), a signing failure publishes nothing (`crates/notaio/src/audience.rs`). |
| The integrity of notaio's own image, the component that signs policy | Built only by this repository's CI on native runners, keyless Cosign signature by digest, CycloneDX SBOM, build provenance (`actions/attest-build-provenance`); each release attaches its install manifest pinned to the image digest and signed (ADR-0009, `.github/workflows/build.yaml`). The release logic is tested on every pull request (`release-manifest-test`, `set-version-test`). |
| Metric "relaxations past their expiry: 0" and the relaxation dashboard | `notaio_relaxations_past_expiry` (active grants past `expiresAt`, must be 0), and per active grant `notaio_relaxation_age_seconds` and `notaio_relaxation_expires_in_seconds`, served on `/metrics` (ADR-0010, `crates/notaio/src/metrics.rs`). `e2e_install` reads the deployed value. A Grafana dashboard over them ships in `deploy/monitoring/`; the Prometheus and Grafana are the site's. |
| A fail-open bug in the evaluator | a guard independent of `evaluate` refuses to sign a bundle without a ceiling, with an error finding, with an expired relaxation, or already past `notAfter`; `Ready=False, FailOpenRefused` and `notaio_fail_open_total`, which must be 0 (ADR-0010, `crates/notaio/src/guard.rs`). The same guard runs before an audience bundle is signed, for the checks that apply to one (an error finding, already past `notAfter`); an audience has no ceiling of its own, so the ceiling check is the granting policy's. |
| Known vulnerabilities in notaio's image | Grype scans every published image (ADR-0012), its SBOM covering every Rust crate (`cargo auditable`), findings in Code Scanning, the build failing on a fixable High or Critical. Findings that cannot affect notaio are suppressed only by OpenVEX statements in `.vex/`, each backed by a fact about the binary that `make vex-evidence` re-checks on every pull request; the VEX document is attested to the image and attached to each release. cargo-audit and cargo-deny cover the Rust dependencies on every change. |
| The definition of an audience (how its credential is obtained and placed, where it is reached) is signed like the policy (T5.4, T8.2 applied to definitions) | `SandboxAudience` compiled into a signed audience bundle, published to `<audience>-audience` and owned by the audience, a finding keeping the last valid bundle until it expires (`crates/sandboxpolicy-core/src/audience.rs`, `crates/notaio/src/audience.rs`, ADR-0020; `e2e_audience`). Off until `NOTAIO_AUDIENCE_PLATFORM_NAMESPACE` is set; while it is unset nothing here changes and the definitions stay in the consumer's own configuration. |
| A team's audience stays within its namespace and its own credential (K5.3, T5.3) | A team audience may not mint, refresh or exchange with the consumer's keys (L022) or read the platform's OpenBao (L023); its `secretRef` and `caRef` carry no namespace, so they resolve in its own; it is granted only from its own namespace (L027); no team name shadows a platform audience (L024); a grant never exceeds its definition (L028); header names cannot reframe a request (L026). Collisions refuse the newcomer, so a platform audience added later cannot break a team's; an audience that was never published refuses nothing and the platform wins a tie between two edited audiences, so a team cannot withdraw a platform audience by parking a colliding one (`refused_in_collision`). Standing is read from the audience's status, which only notaio may write (ADR-0021). Header values cannot carry a line break (L026). All in `notaio lint --platform-audience-namespace` and the controller. |
| A policy's name used to take over another ConfigMap in its namespace (T8.2: what the controller may write) | notaio publishes only to a ConfigMap that is free or carries its own `managed-by` label; one that is not its own is never written, never owned, and its annotations never read as a version: `Ready=False, BundleNameTaken` (`crates/notaio/src/adopt.rs`, ADR-0003 decision 1 as amended; `e2e_bundle`). |
| notaio's own record, read back as input (T8.2 applied to status) | notaio computes the next bundle version from the previous status and the published ConfigMap, schedules refreshes from `status.bundleNotAfter`, and decides an audience's standing in a collision from its published digest. It also reads a composite's `status.includes` back, only to route an include's change to the composites that took it (ADR-0023); a forged entry could cause an extra evaluation, never a grant. Only notaio's ServiceAccount may write the status of `SandboxProfile`, `SandboxPolicy`, `KnobGrant` and `SandboxAudience`, cluster-admin included (`sandbox-status-notaio-only` in `deploy/admission/gitops-only.yaml`, ADR-0021; `e2e_admission`). Remaining: whoever can write ConfigMaps in a policy namespace can raise the version annotation, bounded by `next_version`, or delete the bundle, an outage until the next refresh. |
| A policy composed of others (ADR-0023): no union nobody approved, no grant nobody wrote, no eligibility widened through an include (O3, K7.2, T8.2) | `compose` in `crates/sandboxpolicy-core/src/compose.rs`, run by the controller and `notaio lint` alike. An include contributes only named audiences, egress and tools; everything sandbox-wide, knobs and the KnobGrants that relax them included, is the composite's own, so an include's relaxation never reaches a composite. Two includes supplying one key are refused, never merged (L031); includes are one level deep and at most four, so there is no cycle (L032); every group the composite names must be in every include's groups (L033); lint and the ceiling run on the effective content, a finding naming the include it came from. A missing include (`IncludeNotFound`) or any refusal publishes nothing and the last bundle expires (ADR-0018). A `publish: false` policy is linted but never compiled or signed (`NotPublished`). An include is resolved only in the composite's namespace. The controller re-evaluates every composite of a changed or deleted include through a watch, so a narrowed include narrows its composites within the tightening latency (`crates/notaio/src/include.rs`, `e2e_compose`). |
| Policy profiles as reviewed bundles of knobs (section 10) | `builtin.rs`, `deploy/profiles/builtin.yaml` |

## Supported, enforced elsewhere

| Model item | Where |
| --- | --- |
| T8.2 silent edit of a policy | `deploy/admission/gitops-only.yaml` here (ExposureCeiling and SandboxAudience included), tested by `e2e_admission` on kind and k0s, plus review in the policy repository. The two-person review rule is a repository setting. The controller cannot edit policy objects either (`10-rbac.yaml`, `e2e_rbac`). Before admission, optionally, signed delivery (ADR-0015): Flux applies a policy only with CI's signature from the default branch, and a ceiling only with Security's own, whoever can push; residual risk, a CI-signed policy proves a build and not a review, bounded by its Security-signed ceiling. Where teams deliver their own audiences and policies (ADR-0020, decision 12), each team namespace admits only its own GitOps identity: a binding per namespace, a deployment requirement this repository documents (`docs/src/guides/platform-audiences.md`) and does not ship. Status, which the spec rule does not match, is written only by notaio (ADR-0021). An include lives in its composite's namespace, so it is admitted by the same rule and the same identity; its owner can still change every composite that takes it (ADR-0023), which is visible in the include's `status.includedBy` and bounded by each composite's own ceiling. |
| Profile eligibility by group (K7.2, T7.3) | Banlieue admission, using these objects as parameters |
| Enforcement of egress, tools, leases, budgets, jail and guard settings | Gateway, mediatore, mediatore-guest, from the bundle. Distribution (ADR-0003): mediatore reads the bundle ConfigMap through the API and verifies it. Guests do not verify bundles yet: mediatore-guest does not link `sandboxpolicy-bundle` and receives what the broker derives from a verified bundle; verification in the guest is planned (roadmap 00 phase 3), and `make bundle-deps-check` keeps the crate fit for it. mediatore reads and verifies every bundle and reports each gap between its configuration and the bundle, enforcing nothing (roadmap 00 phase 1); its gateway can serve a bundle's direct egress behind a switch that defaults to shadow. Enforcement is roadmap 00 phases 2 to 4. |
| Token minting per policy and audience (T5.3) | Mediatore |
| Downgrade protection at each consumer (T5.4) | A consumer keeps a floor on its own storage with `sandboxpolicy_bundle::floor::accept`, which also refuses another policy's bundle, or with `check_policy` and `next_floor` when its store is not a `VersionFloor` (ADR-0008). The maximum lifetime applies to every consumer that verifies with `VerifyOptions::at`, mediatore included, once it takes this crate version. mediatore uses `verify_bundle` and `next_floor` over its store, moved by a compare and set, and refuses a bundle whose signed namespace is not the one it was read from (roadmap 00 phase 1); the guest keeps none yet (phase 3). For audience bundles, `floor::accept_audience` and `next_audience_floor`, adopted by mediatore in its ADR-0055. |
| Resolving an audience's credential, and refusing collisions on what it reads | mediatore (its ADR-0055): reads only signed audience bundles, derives platform or team from the namespace with its own configuration, resolves a team's `secretRef` in that namespace only (RBAC `resourceNames`), refuses a team audience from another namespace and a name or endpoint held twice. |

## Not covered yet

| Model item | Gap |
| --- | --- |
| Knob prerequisites proven by passing control tests | Grants record approvals, not test results |
| The credential behind an audience | notaio signs the reference (`secretRef`, an OpenBao path), not the secret: whoever can write the Secret changes the credential, as with a mounted file today. The Secret's writers are the team's or the platform's own (ADR-0020). |
| Which include a grant came from, in the signed record | Until bundle schema v4 (ADR-0023 decision 7), a composite's bundle carries its effective content only; the includes and their content digests are in the composite's `status.includes`, which is not signed, so a consumer's audit line and `PolicyConformant` cannot yet name the include a finding is about. Enforcement is unaffected: the signature covers what is enforced. |
| Monitoring of audience bundles | No per-audience metrics yet: audience bundle age, `Ready` and near-expiry are visible in status and Events only, not in `/metrics` or the shipped alerts. |
